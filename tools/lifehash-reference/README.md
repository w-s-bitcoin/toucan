# C++ reference parity

The JUnit tests check every pixel indirectly through SHA-256 against committed
fixtures generated by [bc-lifehash](https://github.com/BlockchainCommons/bc-lifehash)
commit `0444dbed5615fbc9a98163608c6499c025b7873b`. It needs no C++ compiler or network.
The fixtures contain dimensions and a SHA-256 digest of the complete RGB/RGBA
byte buffer, without a file header, compression, or color conversion. Separate
numeric fixtures compare exact double bits at precision, modulo, and hue-sector
boundaries, including a hue that distinguishes `floorf` from double-precision floor.

The image corpus contains:

- 4,111 VERSION2 fingerprints: 15 fixed public examples/boundaries, followed by
  the first four bytes of SHA-256 of UTF-8 `"SeedSigner LifeHash public test fingerprint " + i`,
  for decimal indices 0 through 4095. Fingerprint hex is decoded directly into
  four bytes, without byte reversal; `makeFromData`, module size 1, no alpha.
- 105 cases covering all five versions, empty input and lengths around SHA-256
  block boundaries, the data/digest/UTF-8 APIs, Unicode, module sizes 1/2/3, and alpha.

This is reproducible differential sampling, not a proof over all 2^32 fingerprints
or every possible input. A pixel digest mismatch identifies the complete input and
options; the runner below identifies the first differing pixel and color channel.

## Numerical target

The C++ output itself depends on the compiler and build flags. The pinned source
revision alone does not define a universal result across every C++ build. These
fixtures deliberately target `-std=c++17 -O3 -ffp-contract=off`, with separate
multiply/add rounding matching Java's specified arithmetic. Do not use fast-math
for this reference target.

For example, a build that enables fused multiply-add contraction can change white
luminance from `0x1.564cdep-1` to `0x1.564cdcp-1`. The compared builds produced the
same pixel bytes in the tested image corpus, but that does not establish identical
intermediate arithmetic or parity across all compilers, flags, or inputs.

## Reproduce or expand the comparison

Requirements: Python 3, Git, a C++17 compiler, and a Java 17+ JDK. Obtain the reference
explicitly once (the runner itself never downloads or modifies a reference clone):

```sh
git clone https://github.com/BlockchainCommons/bc-lifehash.git /tmp/bc-lifehash
python3 tools/lifehash-reference/compare.py --reference /tmp/bc-lifehash
python3 tools/lifehash-reference/compare.py --reference /tmp/bc-lifehash \
  --seed 'Sparrow LifeHash C++ differential test ' --count 16384
```

The runner exports only committed source objects from the pinned revision into a
temporary directory, compiles C++ with `-std=c++17 -O3 -ffp-contract=off
-include stdexcept -include cstring`, and compiles the current Toucan source with
`javac --release 17`. It compares raw pixel buffers
byte-for-byte and checks dimensions. Temporary inputs/outputs are removed when it
exits. `--cxx`, `--java`, and `--javac` select compiler/runtime executables.
The forced includes supply declarations missing from the pinned `hex.cpp`
(`<stdexcept>`) and `lifehash.cpp` (`<cstring>`), which newer libstdc++ versions
require. They do not modify the exported reference source. The runner prints all
compiler flags; fixture headers retain the numerical-target flags so adding these
portability includes does not change otherwise identical fixture files.

To intentionally regenerate the committed fixtures from C++:

```sh
python3 tools/lifehash-reference/compare.py --reference /tmp/bc-lifehash \
  --write-fixtures src/test/resources/com/sparrowwallet/toucan/lifehash-reference.txt \
  --write-numeric-fixtures src/test/resources/com/sparrowwallet/toucan/numeric-reference.txt
```

Expected values are generated solely from C++; Toucan is used only for comparison.
Regeneration writes files only after the full image comparison passes. Review any
fixture diff against the pinned reference before accepting it, then run the JUnit
suite. Keep the default seed/count when rebuilding the committed corpus.
